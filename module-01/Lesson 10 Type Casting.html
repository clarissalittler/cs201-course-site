Lesson 10: Type Casting

NOTE: This is a summary of chapter 2, sections 2.2 and 2.3 in the textbook.

Converting Between Unsigned and Signed

When typecasting (changing from one type to another type) between corresponding signed and unsigned types, C defines the result by value: conversion to unsigned uses arithmetic modulo 2w. On the two's-complement systems used in this course, a same-width conversion therefore preserves the bit pattern and changes how those bits are interpreted. (Conversions between different sizes are covered later in this lesson.) This can lead to several problems.

When going from same-sized (number of bits) signed to unsigned, if the signed value is guaranteed to be positive there is no problem as the bit pattern is the same for positive numbers between signed and unsigned. However, if the signed number turns out to be negative the result will be a positive number not even in the same ballpark. For small negative numbers, the result ends up being a very large positive number.

Even with positive values, converting from unsigned to signed can be surprising. Signed and unsigned types of the same width have the same number of bit patterns, but the signed type uses part of its range for negative values. If the unsigned value is larger than TMAX, the C standard says the result is implementation-defined (or an implementation-defined signal may be raised). GCC and Clang on the two's-complement systems used in this course preserve the low-order bits, which commonly makes a value with its top bit set appear negative, but portable code should not depend on that result.

Typecasting From Smaller to Larger: Expanding Numbers

Changing numbers from smaller to larger sizes requires expanding the number by adding bits to the left of the smaller number to create a larger number. For unsigned numbers, this is done by adding zeros. This is called zero extension.

For signed numbers, the left bits are filled in with whatever the left-most bit of the original smaller number was. This is called sign extension and is similar to the right shift's arithmetic shift. This is done to preserve the sign and magnitude of negative values.

Typecasting from Larger to Smaller: Truncation

If the original value fits in the destination type, conversion preserves the value. If it does not fit and the destination is unsigned, C defines the result modulo 2w; on ordinary hardware this keeps the low-order bits and discards the rest. If the destination is signed and the value does not fit, however, the result is implementation-defined (or an implementation-defined signal may be raised). Common GCC and Clang targets also keep the low-order bits here, but portable programs should validate the range before a narrowing signed conversion.

Implicit Typecasting with Mixed Signed and Unsigned Values

When doing arithmetic or doing comparisons, the compiler does implicit typecasting when there is a mixture of signed and unsigned values. The C rules (called the usual arithmetic conversions) depend on the relative rank of the two types:

  • First, the integer promotions are applied: operands of types smaller than int (such as char and short) are promoted to int before any arithmetic is done.
  • If the operands have the same rank, the signed operand is converted to unsigned. For example, int mixed with unsigned int → both become unsigned int.
  • If the signed type has a higher rank and can represent every value of the unsigned type, the unsigned operand is converted to the signed type. For example, on a typical Linux system unsigned int mixed with long → both become long (because long is 64 bits and can hold every unsigned int value).
  • Otherwise, both operands are converted to the unsigned version of the higher-ranked type.

The rule that matters in practice: int compared against unsigned int is the dangerous case — the negative int gets reinterpreted as a huge positive value. It is recommended not to rely on the compiler to silently choose, especially in comparisons (see textbook for some interesting effects).
