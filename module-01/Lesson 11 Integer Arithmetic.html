Section 2.3: Integer Arithmetic

I have to admit that I was expecting this section to discuss how arithmetic is performed in hardware, but it seems like the authors decided this wasn't as important. The section seems to be more about one consequence of doing arithmetic: overflow. Overflow occurs when the full integer result cannot fit within the size limits of the data type.

I guess the reason might be that the underlying mechanism of doing arithmetic tends not to have an effect on software developers until overflow occurs. So knowing about overflow, when it happens and how to detect it, is more important from a programmer's perspective than how arithmetic is performed in hardware.

Overflow In Unsigned Addition

In order to hold the sum of two unsigned numbers of w bits, the resulting size needs to be 1 bit more or w+1 bits. For example, if you are using two 8-bit numbers, the sum might need 9 bits to prevent overflow. This represents a range that is twice the range of the two numbers.

For example, the maximum for 8-bit unsigned is 255. Adding two 255 numbers together gives a sum of 510 which will fit in a 9 bit range where the maximum number is 511. Basically, the maximum overflow from addition only requires one more bit to hold the results without overflow.

When overflow occurs, the leftmost bits are ignored. This will cause the sum value to become smaller than either of the two operands (this is proven mathematically in the textbook, so I won't prove it here). This gives us a good way to detect if an overflow has occurred by checking the sum against either of the two operands to see if the sum is smaller. A sum of two positive numbers (remember this is unsigned) is always going to be larger unless overflow occurs.

Overflow in Signed Addition

Addition for two signed integers also needs at least 1 extra bit to fit any sum. Again, this is based on the largest value possible being added to itself (see unsigned). However, overflow can only occur when the two operands have the same sign (either positive or negative). If x and y are both negative, this is called negative overflow. If x and y are both positive, this is positive overflow.

At the hardware level, if we keep only the low w bits, negative overflow produces a non-negative wrapped bit pattern (the edge case TMIN + TMIN wraps to 0), while positive overflow produces a negative one. This explains the processor's overflow flag. It does not make a wrap-after-the-fact test valid in portable C, because evaluating an overflowing signed addition is already undefined behavior.

Important caveat about signed integer overflow in C: Although the underlying x86 hardware wraps around predictably as described above, the C standard says that signed integer overflow is undefined behavior. Modern compilers (GCC, Clang) at -O2 and higher routinely exploit this fact, sometimes deleting overflow checks that depend on the wrapped result. The wrap-based detection idioms shown in this lesson work as written for unsigned arithmetic, but for signed types you should either use unsigned arithmetic, use compiler builtins like __builtin_add_overflow, or check for overflow before performing the operation.
WARNING: The above methods are guaranteed to detect overflow. However, using this method: 
if(x == (sum-y))
         // this is okay
else
         // this is overflow 
turns out not to work for overflow detection because x == (sum-y) is always true in modular arithmetic (adding y and then subtracting y wraps back to the original x), so this test never detects overflow.

Two’s Complement Negation

The negation of a signed number is changing the sign of the number while keeping its magnitude. There is no equivalent to negation in unsigned numbers.

For the range of signed numbers, remember that there is one extra negative value than positive value. This has an effect on TMIN because there is no positive value with the same magnitude: TMAX is one smaller. There is therefore no representable result for -TMIN. On ordinary two's-complement hardware the same bit pattern may appear to come back, but in C the expression overflows and has undefined behavior. Do not use the following program as an overflow test:

int min = INT_MIN;
int nmin = -min;
printf("%d %d\n", min, nmin);

The safe takeaway is to check for TMIN before negating a signed integer.

Overflow in Multiplication

For multiplication, both signed and unsigned need 2*w bits. For example, if we are multiplying two 8-bit numbers, the result may need 16 bits to fit in memory without overflow. This is much more severe than with addition, making multiplication more prone to overflow problems.

For unsigned multiplication, the result is reduced modulo 2w, which is equivalent to keeping the low-order bits. Processor hardware also produces those low bits for a signed multiply, but an out-of-range signed result is undefined behavior in C. Under an explicitly chosen wraparound model, the following textbook identity can detect multiplication overflow:

mult = x*y;
    if ( x == 0 || mult/x == y)
       // this is okay
    else
       // this is overflow

works under two's-complement wrap semantics (see problem 2.35 in the textbook, which proves it assuming the multiplication wraps). Two caveats apply in real C code: for signed types, the overflow in x*y is undefined behavior (see the warning box above), so the compiler is not obliged to produce the wrapped result the proof relies on; and the case x = -1, y = INT_MIN makes mult/x itself overflow (INT_MIN / -1), which raises SIGFPE and crashes the program on x86-64. The robust practice is to use the compiler builtin __builtin_mul_overflow.

Multiply and Divide by Powers of 2

Right and left bit shifting can sometimes express multiplication or division by a power of 2. Optimizing compilers already choose an appropriate shift or multiply instruction, so write the clearest correct expression and let the compiler optimize it. The equivalences below are simplest for unsigned values; signed values require the caveats that follow.

The left shift operator does multiplication:

num << i => num*2i

The right shift operator does division:

num >> i => num/(2i)

Right shift on signed numbers is implementation-defined in C: C23 mandates two's-complement representation, but right shift of a negative signed value remains implementation-defined even in C23 (it was C++20 that defined it as an arithmetic shift). In practice, every mainstream compiler (GCC, Clang, MSVC) performs an arithmetic shift (sign-extending). Note that for negative numbers, arithmetic right shift rounds toward negative infinity (floor division), whereas C's / operator truncates toward zero. For example, -7 >> 1 gives -4, but -7 / 2 gives -3.

For unsigned values, left shift is defined modulo 2w. For signed non-negative values, left shift is defined only when the mathematical result is representable; otherwise the behavior is undefined. The right-shift equivalence for negative signed values depends on the implementation and rounds differently from C division on the systems described above.
