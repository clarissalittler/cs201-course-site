Signals in Linux Systems

Signals are higher-level or software-level exceptions that processes, including the operating system, can send to other processes (or to itself). These can be 'caught' by the process through a signal handler: a function that is to be called when the signal is caught by the process. If the process doesn't have a signal handler, the operating system has a default action that it takes.

The list of POSIX signals on the Signals (IPC) wiki shows all of the 31 standard signal types that can be sent in a Linux system. You don't need to memorize these signal types. Below is a list of some important signals:

  • SIGINT (2): default action: terminates
    this is sent to the foreground process running in a terminal when the user hits <ctrl> c. Also, can be sent to any user process by using the command "kill -2".
  • SIGFPE (8): default action: terminates with core dump
    Called a 'floating point exception', it is sent when dividing by 0 is attempted. Ironically, by default, floating point divide by zero isn't affected by this signal, only integers are.
  • SIGKILL (9): default action: terminates
    can send this by using the command kill -9 followed by the PID of the process. This is one of two signals that can't be overridden by a signal handler.
  • SIGSEGV (11): default action: terminates with core dump
    the infamous 'segmentation fault' when accessing invalid memory.
  • SIGALRM (14): default action: terminates
    can be used to set up a one-shot timer. The alarm() function sends this signal once after n seconds. To get repeated alarms, alarm() must be called again (e.g., from within the signal handler).
  • SIGCHLD (17): default action: ignores
    sent by the kernel to a parent process when one of its children terminates, stops, or resumes (the child does not call kill() itself; the kernel generates and delivers SIGCHLD on the parent's behalf).
  • SIGCONT (18): default action: continues a stopped process
    Sent to resume a stopped process. A caught SIGCONT also resumes the process before its handler runs.
  • SIGSTOP (19): default action: stops until SIGCONT
    Sent to a process to stop or suspend a process. This is NOT sent from the terminal when hitting <ctrl> z. SIGSTOP can be sent by any process with permission (e.g., kill -STOP <pid>) or by debuggers and job-control mechanisms. Like SIGKILL, its behavior cannot be caught, blocked, or ignored — these are the two signals that can't be overridden by a signal handler.
  • SIGTSTP (20): default action: stops until SIGCONT
    Sent from the terminal when hitting <ctrl> z. Unlike SIGSTOP, SIGTSTP can be caught, blocked, or ignored by a signal handler — that's how programs like text editors and shells decide what cleanup to do (saving cursor position, restoring terminal modes, etc.) before suspending.

SIGCHLD and Reaping Children: The Classic Pattern

SIGCHLD ties directly back to the zombie problem from Lesson 6. Because the kernel sends SIGCHLD to the parent whenever a child terminates, a parent doesn't have to sit blocked in waitpid() waiting for children to finish. Instead it can install a handler for SIGCHLD (using the functions we'll see in the next lesson) and do the reaping there:

void sigchld_handler(int sig)
{
    int saved_errno = errno;
    int status;
    (void)sig;
    // reap EVERY zombie that is ready, without blocking
    for (;;) {
        pid_t pid = waitpid(-1, &status, WNOHANG);
        if (pid > 0) continue;
        if (pid == -1 && errno == EINTR) continue;
        break;  // 0: none ready; -1: no children or another error
    }
    errno = saved_errno;
}

Include <errno.h> for errno and <sys/wait.h> for waitpid(). Saving and restoring errno prevents an asynchronous handler from changing an error value the interrupted code was about to inspect. The WNOHANG option (from Lesson 6) makes waitpid() return immediately with 0 when children remain but none has a reportable state change, or -1 with ECHILD when no matching children remain, so the handler never blocks. The reaping loop matters because ordinary standard signals are not queued: multiple occurrences can collapse into one pending signal. If three children terminate in quick succession, the parent may therefore observe only one pending SIGCHLD. Reaping in a loop until waitpid() has nothing left picks them all up. POSIX real-time signals have different queuing rules.

We'll discuss how a process can deal with some of these in a later lesson.
