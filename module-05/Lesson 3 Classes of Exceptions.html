Classes of Exceptions

The single most useful axis to organize exceptions on is synchronous vs. asynchronous: was the event caused by the instruction the CPU was just executing (sync), or did it come from outside (async)? Synchronous means tied to the instruction that causes the event, not necessarily repeatable across runs: a load might page-fault on one run but find its page resident on another. Asynchronous events arrive independently of the instruction stream.

The textbook splits exceptions into four classes. Three of them are synchronous (caused by the current instruction); only interrupts are asynchronous.

InterruptAsyncAn I/O device signaling the CPUService the device, then resume the next instruction

Now the details of each class:

  • Interrupts: these occur asynchronously — the CPU was executing one of your instructions and the network card finished receiving a packet, or the disk controller finished a read, or the timer's quantum expired. The hardware sets a "pin" on the CPU; the CPU notices once it finishes the current instruction and jumps to an interrupt handler. The exception number on the bus tells it which handler. Because interrupts can happen at any time, kernel code that protects shared data has to disable interrupts (or use locks) for any region that the handler might touch.
  • Traps: these are synchronous and intentional. The program executed an instruction whose entire purpose is to trigger a trap, almost always to ask the OS for service. The canonical example is the syscall instruction (Module 3 Lesson 4), which the kernel handles by reading the syscall number out of %rax and dispatching to the right kernel routine. Debuggers also use traps via the int3 breakpoint instruction. After the handler runs, execution continues at the next instruction.
  • Faults: these are synchronous and unintentional. The program tried to do something it can't do at the moment, and the CPU traps to a fault handler that tries to fix the situation. If it can, the handler returns and the same instruction re-executes — this time successfully. The page fault is the most common example: your program touches a virtual page that's been swapped out, the kernel reads it back from disk, and the access succeeds the second time around. If the fault is unrecoverable (NULL dereference, divide by zero), the kernel turns it into a fatal signal and the process dies.
  • Aborts: these are synchronous too, but the hardware has determined the situation is unrecoverable. There is no resuming. The classic example is the machine check exception, raised when the CPU detects something like uncorrectable ECC errors in DRAM. The system typically panics. Faults and aborts shade into each other on real CPUs — for example, integer divide-by-zero is technically a fault, but Linux turns it into a fatal SIGFPE which makes it look like an abort from a user's perspective.
