Part A: Exceptions (Lessons 1–4)

Exceptions

The umbrella name for all the events that cause exceptional control flow is exceptions. An exception is an abrupt change in control flow that comes from a change in the processor's state — either something the running instruction did (such as dereferencing a null pointer and triggering a segfault), or something completely external (such as a network card noticing a packet has arrived).

Let's walk through what mechanically happens. Imagine your program executes movq (%rax), %rbx and %rax happens to be 0. The CPU tries to read from address 0, the MMU detects that address 0 is unmapped, and the CPU raises exception number 14 (the page fault). What happens next is a four-step dance:

  1. Look up the handler. Long before any of this happened, the OS set up an exception table in memory: an array indexed by exception number, where each entry is the address of an exception handler. Entry 14 holds the address of the kernel's page-fault handler.
  2. Save the user state. The hardware pushes some processor state (at least the faulting instruction's address and the flags) onto the kernel stack so it can resume the user program later.
  3. Transfer to the handler. The CPU switches to kernel mode and jumps to the handler's address. From the user program's perspective this is a procedure call it didn't make.
  4. Decide what to do. The handler runs. When it finishes, one of three things happens:
    • Resume the same instruction. The handler fixed the underlying problem (e.g., paged in a missing page). The faulting instruction re-executes, this time successfully. (This is what makes virtual memory work.)
    • Resume the next instruction. The exception was triggered intentionally by the program (e.g., a system call). The instruction after the trap-causing one continues.
    • Abort the program. The exception is fatal (e.g., dereferencing a NULL pointer in a process with no handler). The OS terminates the process and returns control to the rest of the system.

You'll see this same four-step pattern over and over in the rest of the module. What changes is which exception number gets raised, who runs the handler, and what the handler decides to do.
