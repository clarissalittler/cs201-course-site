Flow Control

Up to now, every control transfer in your assembly programs has been requested by the program itself: a jmp, a je, a call, a ret. The CPU just walked from one instruction to the next, occasionally taking a branch when the program asked it to. We call this sequence of transfers the program's flow of control or control flow.

This module is about everything that happens when control transfers without the program asking. Think about pressing Ctrl-C in a terminal: the program was happily running an infinite loop, and a fraction of a second later it has died. Nothing in the program's source code says "exit on Ctrl-C." Yet the keypress somehow reached into the running process and stopped it. How?

The answer is something the textbook calls exceptional control flow (ECF) — abrupt changes to a process's flow that the process itself did not initiate. ECF is the mechanism behind a long list of things you already use without thinking about them:

  • A hardware timer fires every few milliseconds so the OS can rotate through running processes.
  • You request data from a disk; the disk eventually finishes and signals back.
  • A child process dies and the parent gets notified.
  • You hit Ctrl-C and the program receives SIGINT.
  • You divide by zero, dereference a null pointer, or call a system call.

All of these are detours: the program was doing one thing, an event happened, and control jumps elsewhere. Over the next dozen lessons we'll work through the four kinds of events that cause these detours (interrupts, traps, faults, aborts), the operating-system abstractions built on top of them (processes, fork/exec/wait), and a major user-visible application of all that machinery (signals).
