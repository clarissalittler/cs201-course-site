Part B: Processes (Lessons 5–7)

Processes

To understand better how exceptions are handled, it helps to understand the workings of processes. According to the textbook, "A process is the instance of a program in execution". A program is a series of instructions that are run as a process (or as several processes as a program can be executed several times concurrently).

A process runs in a context which consists of the sum total of state (or information) needed to successfully run the process to completion. This state includes:

  • the program’s code and data stored in memory
  • its program stack
  • the contents of its general-purpose registers
  • its program counter
  • environment variables
  • the set of open file descriptors

When a program name is invoked at the command line (shell), the shell program creates a new process and the context needed to run the process to completion. An application program can also create a new process. This is called forking and we will talk more about this in the following sections.

How the operating system handles processes is complex. The textbook only discusses two things the operating system provides processes:

  • logical control flow.
  • address space.

For each process, these are independent from all other processes. This gives the illusion from a process's perspective that they have exclusive use of the CPU and the memory space.

Logical Control Flow

This is defined in the book as the series of PC (program counter) values that the CPU runs for just this one process. Basically it's the sequence of instructions a process is running from beginning to end. This is also abbreviated to logical flow.

A process is typically running concurrently with other processes in the system. This means that its logical flow overlaps in time with other processes. This makes it seem like these processes are running at the same time. However, if they share a CPU, only one process can run at the same time.

How does the operating system and hardware run several processes on the same CPU? This is done by interleaving the running of the processes. Each process takes turns using the CPU and memory for very short imperceptible time intervals.

  CPU usage over time (single core, four processes A, B, C, D):

   time ->
   |---------------------------------------------------------------|
   | A | B | A |  C  | D | A |  B  |  C  | A |  D  | B |  C  | A   |
   |---------------------------------------------------------------|
       ^   ^                  ^                          ^
       |   |                  |                          |
       |   `-- preempted, OS chooses next process        |
       |                                                  |
       `------ time slice ends, OS runs briefly  ---------'

  At any single instant, only ONE process is executing on this CPU.
  But across a wall-clock second, every process gets some CPU time,
  giving the illusion that they all run at once.

Above is an illustration of what interleaving is. There are 4 processes running on one CPU. They take turns running a portion of their instruction set before being preempted which means being suspended for a time. Each 'time slice' has one process running for a variable amount of time. How long and what process to run next is called scheduling and is decided by the operating system, which is run in between time slices.

The textbook puts more emphasis on a one-CPU system, but most modern CPUs have multiple CPUs called cores. The textbook does this for keeping the discussion simple and not having to get into the complex intricacies of scheduling on a multi-core CPU. So the picture of how programs are run is more complex than what's being presented here.

The preempting is done via a hardware interrupt that goes off every few milliseconds. This causes the currently running process to stop running (be preempted), the context is saved and the operating system's kernel is run. This is to allow the operating system to do its own tasks in-between each process (this is assuming it doesn't run in its own core). When the operating system is done it will choose another process to run and preempt itself.

Concurrent Flows

When one process's execution time overlaps another process's execution time they are said to be concurrent. Concurrency comes in two types: interleaving and parallelism. Interleaving is described as above. In today's multi-core systems, it's possible to have two processes concurrently run side-by-side (no interleaving) in two different cores. This is called parallel flows, parallel execution or running in parallel.

Private Address Space

Each process is run within a private address space that starts with 0 and goes (theoretically) to the limit set by the machine's address width — on x86-64, user programs see 48 bits of address space (about 256 TiB), regardless of how much RAM is actually installed. In reality, the process is not likely to use all of this space and since portions of memory might be reserved for the operating system, it won't be able to use the full memory that the computer has to offer.

The system manages to create this illusion by mapping the program's addresses to actual physical addresses. Each program running at the same time is given a range of the actual memory addresses (usually this is 'growable' or 'shrinkable' depending on what each program needs). These are mapped starting at 0 and going to whatever the process needs. If the program needs more than the allocated memory it's given, part of the memory may be moved to disk to make room for the creation of more memory. So the same address (say, address 0x1000) in two different processes maps to two different physical memory locations — each process gets its own private mapping. This scheme is called virtual memory.

Figure 8.13 gives a much fuller view of this private address space. Note that the kernel (the core of the operating system) is mapped into the high portion of every process's address space. The kernel uses this region for its own data — I/O buffers for files the process has opened, syscall data, etc. The process itself is not allowed to read or write this kernel region; the MMU catches attempts to do so and the OS turns them into a segmentation fault.

User and Kernel Modes

Ordinary processes need to be restricted in what they can do and access while running; however, the operating system needs full access to everything. So processes can run in two modes: user mode for restricted access and kernel mode for full access. This is determined by a 'mode bit' inside a 'control register' that lets the CPU know whether the process running has access to sensitive parts of memory or can do only restricted tasks.

A process running in kernel mode can execute any instruction in the instruction set and access any memory location in the system. However, a processor in user mode is not allowed to execute privileged instructions that do things such as halt the processor, change the mode bit, or initiate an I/O operation. Nor is it allowed to directly reference code or data in the kernel area of the address space. Any such attempt results in a fatal protection fault. User programs must instead access kernel code and data indirectly via the system call interface.

Initially a process runs in user mode. It can be switched to kernel mode if an exception happens and an exception handler needs to be run. The mode bit is switched and then the exception handler is run in kernel mode. Then it is switched back to user mode to continue to run the rest of the process.

Context Switches

Every time a process needs to be switched out and in, its entire state (or 'context') needs to be switched in and out. The context of each process is kept by the kernel in its part of the memory space. An exception in hardware is used to do context switching.

Switching between processes is called scheduling and this is decided by the kernel's scheduler code.

It's not just interleaving processes on the same core that causes preemptive switching. If a process makes a system call, the process is switched out either because the operating system needs to run or because the process will be waiting on some long running action such as reading from the disk. Interrupts and other exceptions will cause processes to be switched out.

Looking ahead to Module 6: a major theme of this lesson is that processes are deliberately isolated — each one has its own private address space and its own copy of every global variable. That isolation is a feature when you want safety, but it also makes it harder for two pieces of work to cooperate on shared data (you can't just write to a global). Module 6 introduces threads, which look a lot like processes (each has its own logical control flow and stack) but deliberately share the same address space, file descriptor table, and signal handlers. That shared memory is what makes threads cheap to communicate through — and what makes them dangerous in the ways the next module will explore.
