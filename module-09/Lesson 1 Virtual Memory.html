NOTE: This is a summary of chapter 9, sections 9.1 - 9.8 in the textbook.

Why Virtual Memory Exists

In the early days of computing, programs accessed physical memory directly. This created serious problems: a bug in one program could overwrite the memory of another program or even the operating system itself. If two programs happened to use the same memory addresses, they could not run at the same time. And if a program needed more memory than was physically available, it simply could not run.

Virtual memory solves all of these problems by introducing a layer of abstraction between the addresses a program uses and the actual physical memory hardware. With virtual memory:

  • Isolation: Each process gets its own private address space. Process A cannot see or modify Process B's memory, even by accident.
  • Sharing: The physical RAM is shared among all running processes, but each process believes it has the entire address space to itself.
  • Overcommitment: The total virtual memory used by all processes can exceed the amount of physical RAM, because the OS can use disk as overflow storage.

Virtual vs. Physical Addresses

When your C program accesses a variable, the CPU does not send the variable's address directly to the memory hardware. Instead, the CPU generates a virtual address (VA). A hardware component called the Memory Management Unit (MMU) translates this virtual address into a physical address (PA) before the memory access proceeds.

An ordinary pointer to a live object in a user process denotes a location in that process's virtual address space, and debuggers normally display virtual addresses. Null, one-past, invalid, integer-derived, and implementation-specific pointer representations need not denote an accessible location. Physical addresses are normally hidden from application code.

  CPU                    MMU                   Physical Memory
  +----------+      +------------+      +---------------------+
  | generates | ---> | translates | ---> |  actual RAM chips   |
  | virtual   |      | VA to PA   |      |  (DRAM)             |
  | address   |      |            |      |                     |
  +----------+      +------------+      +---------------------+

Pages

Virtual memory divides both the virtual address space and physical memory into fixed-size blocks called pages. On most systems, a page is 4 KB (4096 bytes). The virtual address space is divided into virtual pages (VPs) and physical memory is divided into physical pages (PPs), also called page frames.

At any given time, each virtual page is in one of three states:

  • Unallocated: The page has not been created by the OS. It takes up no space anywhere.
  • Cached: The page is allocated and currently stored in a physical page in RAM.
  • Uncached: The page is allocated but currently stored only on disk (it has been swapped out or has not yet been loaded).

The following diagram shows how virtual pages map to physical pages. Notice that not every virtual page is in physical memory at the same time, and that two different processes can have virtual pages that map to different physical pages:

Page Tables

The mapping from virtual pages to physical pages is stored in a data structure called the page table. Each process has its own page table, maintained by the operating system. The page table is an array of page table entries (PTEs). Each PTE contains:

  • Present bit: Does this entry currently provide a usable translation to a physical page frame? A cleared bit causes a page fault, after which the OS decides whether the address is valid and how to supply it.
  • Physical page number (PPN): If present, which physical page frame holds this virtual page.
  • Permission bits: Can this page be read? Written? Executed? These bits enforce memory protection.
  • Dirty bit: Has this page been modified since it was loaded from disk?
  • Accessed/reference bit: Has this translation been used? Operating systems can use this as one input to page-replacement decisions.

Exact PTE fields are architecture-specific. Information about a non-present page's backing file, swap slot, or virtual-memory area may live partly in software-managed PTE bits and partly in other kernel data structures; a literal hardware PTE does not simply contain the word "disk."

  Page Table (one per process)
  +-------+---------+-----+-------+------+------+
  | Index | Present | PPN | Read  | Write| Exec |
  +-------+---------+-----+-------+------+------+
  |   0   |   1   |  3  |   1   |   0  |   1  |  (code: read+execute)
  |   1   |   1   |  7  |   1   |   1  |   0  |  (data: read+write)
  |   2   |   1   |  5  |   1   |   1  |   0  |  (heap: read+write)
  |   3   |   0   |  -- |   1   |   1  |   0  |  (OS metadata says file/swap-backed)
  |   4   |   0   | --- |   -   |   -  |   -  |  (unallocated)
  +-------+-------+-----+-------+------+------+

To translate a virtual address, the hardware splits it into two parts:

  • Virtual Page Number (VPN): The upper bits, used as an index into the page table.
  • Virtual Page Offset (VPO): The lower bits (12 bits for 4 KB pages), which identify the byte within the page. The offset is the same in both the virtual and physical address.
  Virtual Address (e.g., 32-bit system with 4 KB pages):
  +-----------------------------+------------------+
  |  Virtual Page Number (VPN)  |  Page Offset (12) |
  |       (20 bits)             |     bits          |
  +-----------------------------+------------------+

  Translation:
  VPN ---> look up in page table ---> PPN

  Physical Address:
  +------------------------------+------------------+
  |  Physical Page Number (PPN)  |  Page Offset (12) |
  +------------------------------+------------------+

The TLB (Translation Lookaside Buffer)

Every memory access requires an address translation, but a cached translation does not require rereading the page tables. Without that cache, a single-level table would add one page-table access before the data access. On x86-64, a 4-level hierarchy (or 5 levels with LA57) can require four or five page-table-entry reads on a TLB miss, plus the data access; huge-page mappings can end the walk earlier. Processor caches may satisfy some of those reads, but uncached walks would be prohibitively expensive.

The solution is the Translation Lookaside Buffer (TLB), a small, fast hardware cache inside the MMU that stores recently used page table entries. When the CPU generates a virtual address:

  1. The MMU checks the TLB for the VPN.
  2. TLB hit: The PPN is immediately available. No extra memory access needed. This is the common case.
  3. TLB miss: The MMU performs a page-table walk, traversing each level of the page hierarchy in main memory (4 levels on standard x86-64, 5 with LA57), and stores the final translation in the TLB (possibly evicting an old entry).

Programs with good locality often achieve high TLB hit rates. TLBs are therefore essential to practical virtual-memory performance, while workloads with large or irregular working sets can still spend significant time on page-table walks.

Vocabulary checkpoint

Before going on to page faults, make sure these terms feel solid — you'll see all of them again in the rest of the module:

  • Virtual address (VA) — the address your program sees, e.g., the value of a C pointer.
  • Physical address (PA) — the address used in the processor's physical address space (normally memory, but some ranges can select memory-mapped devices).
  • Page — the fixed-size unit (typically 4 KiB on x86-64) that VM operates on.
  • Frame (or page frame) — the same-sized unit on the physical-memory side.
  • Virtual page (VP) / physical page (PP) — one specific page; VP is in the process's virtual address space, PP is a chunk of physical RAM.
  • Page table — the kernel-managed data structure that maps virtual pages to physical pages, one per process.
  • Page table entry (PTE) — one entry in the page-table hierarchy, containing a physical frame number or next-level pointer plus present, permission, accessed, and other architecture-defined bits.
  • VPN / VPO / PPN — virtual page number / virtual page offset / physical page number. The VA splits into VPN+VPO; translation produces PPN, and the offset is reused to form the PA.
  • MMU — the hardware unit inside the CPU that does the VA-to-PA translation on every memory access.
  • TLB — a small hardware cache of recently used page-table entries, sitting next to the MMU.
  • Page fault — the exception raised for a non-present translation or an access-permission violation; the kernel handler decides whether to supply a page, change a mapping, or reject the access.

If any of those words are still fuzzy, scroll back up before continuing — the rest of the lesson assumes them.

Page Faults

A page fault occurs when translation cannot complete with the requested permissions. Common causes include first access to a valid demand-zero or file-backed mapping, a swapped-out page, copy-on-write, stack growth, a protection violation, or a completely unmapped address. The kernel handler first determines which case occurred:

  1. The CPU generates a virtual address and the MMU looks up the PTE.
  2. The translation is non-present or disallows the requested access, so the MMU triggers a page fault exception.
  3. The CPU transfers control to the OS page fault handler.
  4. The handler consults the process's virtual-memory mappings. If the address or access is invalid, it normally arranges a signal such as SIGSEGV; there is no page to load.
  5. For a valid fault, the handler may allocate a zero-filled page, copy an existing page for copy-on-write, find a page already in the page cache, or read data from an executable, mapped file, or swap.
  6. If a page frame must be reclaimed, a clean file-backed page may simply be discarded; dirty file-backed data may need writeback, and dirty anonymous data may require swap if swap is available.
  7. The handler installs or updates the translation and permissions, then returns. The faulting instruction is normally retried.

A minor fault that needs no storage I/O is much cheaper than a major fault that must wait for a file or swap device, though both cost far more than a TLB hit. Locality helps keep translations and the working set resident.

Demand Paging

Operating systems use demand paging: many mappings are populated only as they are touched rather than reading or allocating every page in advance. Some startup pages and page-table structures are already resident, while first touches of other regions may map page-cache data, allocate zero-filled memory, or read from storage. Over time, the process's working set — the pages it is actively using — tends to accumulate in physical memory.

This is efficient because many programs have large address spaces but only use a small fraction of their pages during any given phase of execution.

Swapping

Under memory pressure, the OS reclaims page frames. It may drop clean file-backed pages (which can be reread), write dirty file-backed pages to their files, or move anonymous pages to a configured swap area. Systems can run without swap. Practical kernels approximate recency and use multi-list or generation-based reclaim policies rather than implementing perfect LRU.

If the system is constantly swapping pages in and out because the working set of all active processes exceeds physical memory, this is called thrashing. Thrashing devastates performance because the system spends most of its time doing disk I/O instead of useful computation.

Memory-Mapped Files

Virtual memory also enables memory-mapped files. The mmap() system call maps a file (or portion of a file) into a process's virtual address space. Once mapped, the process can read and write the file as if it were an array in memory. The OS handles loading pages from the file on demand (using the same page fault mechanism) and writing modified pages back to the file.

Memory-mapped files are used for:

  • Loading program code and shared libraries (the text segment is memory-mapped from the executable file).
  • Sharing memory between processes (two processes can mmap the same file).
  • Efficient file I/O for large files (avoids explicit read/write system calls).

Process Memory Layout Revisited

Now that we understand virtual memory, we can revisit the memory layout of a process with a deeper understanding. Recall the picture from Module 5 Lesson 5 (Processes), which showed each process living in its own private address space with kernel space mapped at the top. Back then we said "each process gets its own address space" without explaining how. Now we can: every region in the layout below is a range of virtual addresses. The OS sets up the page table so that each region maps to appropriate physical pages (or is marked as unallocated).

  High addresses (0xFFFFFFFF on 32-bit)
  +---------------------------+
  |        Kernel space        |  (not accessible to user code)
  +---------------------------+  0xC0000000 (typical on 32-bit Linux)
  |         Stack              |  grows downward
  |            |               |
  |            v               |
  |                            |
  |          (free)            |
  |                            |
  |            ^               |
  |            |               |
  |         Heap               |  grows upward (managed by malloc)
  +---------------------------+
  |   Uninitialized data (BSS) |  global/static vars initialized to 0
  +---------------------------+
  |   Initialized data         |  global/static vars with initial values
  +---------------------------+
  |   Text (code)              |  program instructions (read-only)
  +---------------------------+
  Low addresses (0x00000000)

This diagram uses 32-bit addresses to keep the numbers readable. On the x86-64 machines you are using, the layout is the same but the numbers are larger: virtual addresses are 48 bits, user space runs from 0x0 up to 0x00007fffffffffff, and kernel space occupies 0xffff800000000000 and above.

Each of these regions has different page permissions:

  • Text: Read and execute, but not write. The code is memory-mapped from the executable file.
  • Data and BSS: Read and write, but not execute.
  • Heap: Read and write. Grows upward as malloc requests more memory (via brk/sbrk or mmap).
  • Stack: Read and write. Grows downward as functions are called.
  • Kernel space: Not accessible to user-mode code. Any access triggers a segmentation fault.

A segmentation fault occurs when a process tries to access a virtual address that is either unallocated or that violates the permission bits in the page table entry. The MMU detects the violation and raises an exception, which the OS converts into a SIGSEGV signal that typically terminates the process.

Putting It All Together

Let us trace what happens when your C program executes int x = *ptr; where ptr holds the virtual address 0x00405024:

  1. The CPU sends the virtual address 0x00405024 to the MMU.
  2. The MMU extracts the VPN (upper 20 bits: 0x00405) and the offset (lower 12 bits: 0x024).
  3. The MMU checks the TLB for VPN 0x00405.
  4. If TLB hit: The PPN is retrieved immediately. Skip to step 6.
  5. If TLB miss: The MMU walks the applicable page-table levels. A present, permitted translation can be cached in the TLB. Otherwise a page fault occurs, and the OS may supply a page, handle copy-on-write, or reject the access depending on the mapping.
  6. The physical address is formed by concatenating the PPN with the offset 0x024.
  7. The load checks the cache hierarchy and accesses main memory on a cache miss; the resulting value is placed in a register and then used for x.
