Two's Complement Essentials

  • Negation rule: -x == ~x + 1 (flip every bit, then add 1).
  • Sign bit weight: the top bit contributes -2^(w-1), not +2^(w-1); all other bits keep their usual positive weights.
  • There is exactly one zero (unlike sign-magnitude), so the range is asymmetric: one more negative value than positive.
  • The asymmetry bites: -TMin cannot be represented. Evaluating it is undefined behavior in C; do not rely on the wrapped hardware bit pattern looking like TMin again.
  • Same adder hardware works for signed and unsigned addition; only overflow detection and comparisons differ.

Conversions Between Integer Types

ConversionBit-level effect
Signed ↔ unsigned, same sizeOn our GCC/Linux target, the bits are unchanged. Conversion to unsigned is defined modulo 2w, so (unsigned)-1 == UMax. An unrepresentable conversion to signed is implementation-defined in C.
Widening a signed valueSign-extend: replicate the sign bit into the new upper bits.
Widening an unsigned valueZero-extend: fill the new upper bits with 0.
Narrowing to unsignedDefined modulo 2^w; ordinary hardware keeps the low bits.
Narrowing to signedValue is preserved if representable; otherwise the result is implementation-defined (or an implementation-defined signal may be raised). Common GCC/Clang targets keep the low bits, but portable code must not assume that.
  • Integer promotions: in expressions, char and short are first promoted to int before arithmetic.
  • Usual arithmetic conversions: when a signed and an unsigned operand of the same rank meet, the signed one is converted to unsigned.
  • The classic trap: -1 < 1U is false — the -1 converts to UMax (4,294,967,295), which compares greater than 1.
int  x = -1;
unsigned u = 1;
if (x < u) ...   /* NOT taken: x converts to 4294967295 */

Bitwise vs Logical Operators

BitwiseLogicalDifference
&&&Bitwise works bit by bit; logical treats any nonzero value as true.
|||Logical returns only 0 or 1; bitwise returns a full-width result.
~!~0x41 == 0xFFFFFFBE but !0x41 == 0; !!x normalizes to 0/1.
^(none)XOR has no logical counterpart; x ^ x == 0.
  • Logical && and || short-circuit: the right operand may never be evaluated.
  • Typo hazard: if (p & p->next) is invalid C because bitwise & requires integer operands. Use if (p && p->next); short-circuiting avoids dereferencing a null p.

Shift Semantics

  • Left shift: x << k multiplies by 2^k (bits shifted out are discarded, zeros shifted in). For signed operands, a negative left operand or an unrepresentable result causes undefined behavior, even for -1 << 0.
  • Right shift, unsigned: logical shift — zeros fill from the left; x >> k is x / 2^k (rounding toward zero).
  • Right shift, signed: arithmetic shift — copies of the sign bit fill from the left, so negatives stay negative. The C standard calls this implementation-defined, but every mainstream compiler (gcc, clang, MSVC) does arithmetic shift.
  • Arithmetic right shift rounds toward negative infinity, so -3 >> 1 == -2, not -1.
  • Shifting by k >= w or by a negative amount is undefined behavior (x86 masks the count to the low bits, but do not rely on it).

Rounding

ModeBehavior
Round-to-nearest-even (default)Nearest representable value; exact ties go to the value with an even (0) last bit.
Round toward zeroTruncate toward 0.
Round down (toward -∞)Always round toward negative infinity.
Round up (toward +∞)Always round toward positive infinity.
  • Guard/round/sticky in one line: hardware keeps the two bits just below the last kept bit (guard, round) plus a sticky bit that ORs everything lower, which is enough to round correctly as if the result were computed exactly.
  • Round-to-nearest-even avoids the statistical upward bias of always rounding halves up.

Floating Point Pitfalls

  • 0.1 is not exact: like 1/3 in decimal, 0.1 repeats forever in binary; stored double 0.1 is actually 0.1000000000000000055511...
  • Use == deliberately: exact comparison is correct for values that should be identical (including comparisons with 0 in many algorithms), but it is usually wrong for independently rounded approximations. For approximate comparisons, choose an absolute and/or relative tolerance appropriate to the problem; a single fixed epsilon is not scale-independent.
  • Addition is not associative: in float, (3.14f + 1e10f) - 1e10f == 0.0f because 3.14f is absorbed, but 3.14f + (1e10f - 1e10f) == 3.14f.
  • Large ints lose precision: float has a 24-bit significand (1 implied + 23 stored), so integers above 2^24 = 16,777,216 are not all representable — (float)16777217 == 16777216.0f. For double the limit is 2^53.
  • With IEEE 754's default round-to-nearest mode, overflow goes to ±∞ rather than wrapping, and gradual underflow passes through subnormals on the way to 0. Directed rounding modes and nonstandard flush-to-zero modes change those details.

Common Mistakes Checklist

  • Mixing signed and unsigned in comparisons (-1 < 1U is false).
  • Assuming -x is always positive when x is negative (fails for TMin).
  • Expecting sign extension when widening an unsigned value, or zero extension when widening a signed one.
  • Confusing & with && or ~ with !.
  • Shifting by the type's full width or more (undefined behavior).
  • Assuming right shift of a negative number divides exactly like / (it rounds toward negative infinity, not zero).
  • Forgetting the bias when reading an exponent field: E is e - bias for normalized values, 1 - bias for denormalized.
  • Forgetting the implied leading 1 in a normalized significand.
  • Using == when independently rounded results are intended to be merely close, or using one fixed absolute epsilon at every scale.
  • Assuming every int fits exactly in a float (only up to 2^24).
