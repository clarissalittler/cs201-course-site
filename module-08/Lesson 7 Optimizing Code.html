Lesson 7: How to Optimize Code

How to Optimize Code

The textbook works through a multi-stage optimization example for the next several sections. I think I'll leave the full example to the textbook. Remember to skip 5.7 and 5.9 through 5.12.

Before we get to the list of techniques, here is the unifying frame — every code-level optimization technique below ultimately does one of two things:

  1. Reduce the work the CPU has to do (eliminate redundant function calls, fuse operations, pull invariants out of loops, replace expensive operations with cheap ones).
  2. Expose parallelism the CPU could already exploit (loop unrolling with multiple accumulators lets the CPU's pipelined ALUs work on independent additions in parallel; cache-friendly access patterns let the memory system keep the pipeline fed).

If you ever forget the specifics of a technique, ask: which of those two is it? That's almost always enough to remind you why it works.

Below are the optimization techniques that you should know about for the lab or final exam (optimization will be on the final):

  1. Eliminate Function Calls: Eliminate any function call inside a loop that will always return the same value each time through the loop. Also don't put these calls in the conditional and update parts of the for loop's header as well. There is no reason to keep calling the function every time through the loop if it is guaranteed to give the same value.

    A good example that the textbook talks about is strlen(). It's common to get the length of a string as an upper bound for stepping through a string's characters. Many programmers tend to put the call to strlen() inside the for loop's conditional: 
    for(int i=0; i < strlen(str); i++)
    ....
    but the loop's condition is checked N+1 times (where N is the size of the string), so strlen() ends up being called N+1 times only to return the same value. This is N too many times. A better idea is to call it above the loop and put the value inside a local variable: 
    int size = strlen(str);
    for(int i=0; i < size; i++)
    ....
    This way there is only one function call and the value is probably going to be stored in a register for faster access. In fact, the strlen() function itself goes through the string to find the null value on the end so it is already doing N iterations. Putting it inside the for loop's conditional, it will now do N*N or N2 iterations which is very costly.
  2. Reducing Function Calls: Function calls have non-trivial overhead, so whenever gcc can see the function's body and prove it is safe, it will 'inline' the function (paste the body in at the call site). The main thing that blocks inlining is gcc not having access to the function body — for example, the callee lives in a different translation unit and you didn't enable link-time optimization (-flto), or the call goes through a function pointer or a recursive function. Inlining also runs into limits set by the compiler's heuristics (large bodies, very high call counts).

    So think about whether a function call is necessary inside the loop if the code itself can just be written into the loop. An example from the textbook is the function get_vec_element(). This function is just basically stepping through the array one element at a time; the code for this function can just be copied into the loop for faster performance in accessing array elements (no function call mechanisms to set up and break down).

    Deep, non-tail-recursive functions can be slow for the same reason — lots of nested calls and stack-frame setup. However, recursion isn't always slow: modern compilers often perform tail-call optimization that turns a tail-recursive call into a plain jump (no extra frame, no overhead), and many algorithms (tree traversal, divide-and-conquer like quicksort/mergesort) are clearer and not measurably slower as recursion. The lesson is "prefer iteration when the recursion is deep and non-tail," not "all recursion is bad."

    Of course, you can't eliminate all function calls, but do look at function calls inside hot loops as good candidates for optimization.
  3. Eliminate Unneeded Memory References: Try to avoid directly reading from and writing to arrays and pointers. The compiler usually cannot safely keep them in a register (because of possible aliasing — see the twiddle example in Lesson 5), so each access goes through the memory system — at best a cache hit, at worst main memory. It's best to use a local variable when possible. Local variables end up being stored in registers rather than memory references. So look at how combine4() function (figure 5.10) used the variable acc to avoid a read and write to memory. It can't avoid the read to data[i] entirely but it did cut down the number of memory references from 3 to 1. acc is an example of an accumulator which is very useful in optimizing code.
  4. Loop Unrolling: This is an interesting technique that unfortunately makes code a bit unreadable and may not always work but it's worth trying as it can boost performance under some circumstances. Sometimes gcc will use this method if it feels it's safe to do so.

    Loop unrolling involves doing two or more iterations at one time before going back to the top of the loop. For example: 
    for(int i=0; i < size; i++)
{
   sum += array[i];
}

can be transformed into

int i;
for(i=0; i < size-4; i += 5)
{
    sum += array[i];
    sum += array[i+1];
    sum += array[i+2];
    sum += array[i+3];
    sum += array[i+4];
}

for(; i < size; i++)
{
   sum += array[i];
}
    Note that the last loop is to pick up any leftover array values at the end of the array. Also, note that we need to be careful not to increment past the array size. So basically the first loop stops short of the array size and the rest is picked up in the second loop.

    This is an example of a "5 x 1" loop. The first number represents the number of iterations being done inside the for loop and the second number is the number of accumulators you are using inside the loop. Accumulators are local variables set up to hold the accumulation of results. Using more than one helps with performance as well.

    You can use any number of iterations but there usually is a point where the unrolling stops being effective. How many to use is a matter of trial and error.

    Why does this work? It's not really about the jumps — modern CPUs predict a loop's backward branch almost perfectly, so the jump itself is nearly free. The real win is reduced loop overhead: the counter increment and the conditional test now happen once per five elements instead of once per element, so a larger fraction of the executed instructions are doing useful work. The bigger payoff, though, comes from combining unrolling with multiple accumulators, which exposes instruction-level parallelism (see the 5 x 2 version next).

    You can also help boost things but using two or more accumulators. (this is a 5 x 2 loop): 
    int sum1 = 0;
int sum2 = 0;
int i;
for(i=0; i < size-4; i += 5)
{
    sum1 += array[i];
    sum2 += array[i+1];
    sum1 += array[i+2];
    sum2 += array[i+3];
    sum1 += array[i+4];
}

for(; i < size; i++)
{
   sum1 += array[i];
}
int sum = sum1 + sum2;
    This speeds up code by making each sum independent from each other creating an opportunity for the CPU to use parallelization (or pipelining) when doing the arithmetic on each line. The trick is to alternate the use of each accumulator.
  5. Write Cache Friendly Code: (from Section 6.5 and 6.6)
    Earlier in this module (Lesson 3) we talked about how memory caches work and how they use locality to speed up accessing memory. The principle: access memory with a stride-1 pattern (step through arrays in the same order they are laid out in memory) and reuse values while they are still in the cache (temporal locality). Lesson 8 gives this technique the full treatment, including the row-major vs. column-major matrix examples, so see that lesson for the details.
