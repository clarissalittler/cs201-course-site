Lesson 3: Memory Caches

Common misconception — "the cache is some kind of software." The CPU caches we describe in this lesson are hardware, baked directly into the processor die alongside the cores. You don't allocate them, you don't write to them, you can't even directly observe them — the hardware moves data into and out of them transparently as your program executes regular load and store instructions. (When a Java/Python programmer says "I added a cache" they usually mean an in-memory dictionary they wrote themselves; that's a software cache and is unrelated to what we cover here.)

Memory Hierarchy and Memory Caches

To better exploit locality to speed up delivery of memory data, memory is designed in layers that form a hierarchy. Figure 6.21 in the textbook shows this hierarchy where levels at the top of the memory have faster access times and therefore are more desirable space to store values in. However, because of increased cost and decreased amount of space, these levels are limited in size and can't hold all the data from main memory needed to run a process. Still, they can help by storing a portion of memory that is currently being worked on. This assumes that the software being processed has good spatial and temporal locality.

  Memory hierarchy (smaller, faster, more expensive at the top):

      +-------------------+   ~1 cycle, ~1 KB
      |    Registers      |
      +-------------------+
      |    L1 cache       |   ~4 cycles, 32-64 KB per core
      +-------------------+
      |    L2 cache       |   ~12 cycles, 256 KB - 2 MB per core
      +-------------------+
      |    L3 cache       |   ~40 cycles, 16-64 MB shared
      +-------------------+
      |     Main RAM      |   ~200 cycles, GB scale
      +-------------------+
      |     SSD / disk    |   microseconds (SSD), ms (HDD)
      +-------------------+

  Each level is substantially larger and slower than the one
  above it (the exact ratios vary by level). The CPU walks
  down this stack on every load/store: registers first,
  then L1, L2, L3, RAM.

From fastest to slowest, the levels are: registers, the L1, L2, and L3 caches, main RAM, and finally SSD or disk.

Because of the restraints between size and speed (the larger the cache, the slower the access times), memory caches have become hierarchical in nature over time. The L1 cache is small (typically 32–64 KB per core); it needs to be small in order to keep the access times short. The L2 cache is larger (typically 256 KB to ~2 MB per core on current Intel/AMD desktop chips) and holds more memory but has slower access times. There may also be an L3 cache that is much larger and shared across cores (commonly 16–64 MB on contemporary desktop CPUs, more on server-class chips).

  Multi-core cache layout (typical 4-core x86 desktop):

         Core 0          Core 1          Core 2          Core 3
       +--------+      +--------+      +--------+      +--------+
       |L1d|L1i |      |L1d|L1i |      |L1d|L1i |      |L1d|L1i |
       +--------+      +--------+      +--------+      +--------+
       |   L2   |      |   L2   |      |   L2   |      |   L2   |
       +--------+      +--------+      +--------+      +--------+
            \              \              /              /
             \              \            /              /
              \              v          v              /
               \      +---------------------+         /
                +---->|         L3          |<-------+
                      |  (shared by cores)  |
                      +---------------------+
                                 |
                                 v
                       +-------------------+
                       |       RAM         |
                       +-------------------+

  L1 and L2 are private to each core; L3 is shared.
  L1 itself is typically split into separate instruction (L1i)
  and data (L1d) caches so loading data and fetching instructions
  do not compete for the same cache port.

In many designs (called inclusive caches), each larger cache holds a copy of everything in the smaller cache above it. Other designs use non-inclusive or exclusive policies where the levels may hold different data. The general idea is that the most frequently accessed data ends up in L1 (the fastest cache), and less recently used data migrates to L2 or L3. The larger caches serve as a backstop for data that does not fit in the smaller, faster caches above them.

How Do Caches Work

Note that for the rest of this lesson we focus on a single core. In modern CPUs, the cache system is much more complex. Typically, each core will have its own L1 cache(s) and possibly L2 cache but the L3 cache will be shared between cores (see the multi-core layout above). Also, the L1 cache is typically two caches: one for data and one for instructions. This way loading data doesn't interfere with loading instructions.

When the CPU needs to get a value at a requested address, it looks in the highest cache (L1) and goes down to the lowest cache (L3). If the value is found in one of the caches, this is called a hit. A miss is when the value is not in any cache and needs to be gotten from RAM.

Here is a very simplified example of how caches work. When a process starts running, none of the process's memory is in any of the caches. At some moment, it needs to read a portion of memory, say 1 byte at address 100. The hardware goes to main memory and loads a cache line (a fixed-size block, typically 64 bytes on modern CPUs) containing that address into the caches. The cache line would cover, say, addresses 64 to 127. This line is loaded into both L1 and L2 (we are ignoring L3 for the moment). The hardware loads an entire cache line rather than just the one byte to take advantage of spatial locality: nearby bytes are likely to be needed soon. The next time the program accesses any address within that same cache line (e.g., address 101 or 115), it will be a cache hit — no need to go back to RAM.

  Program asks for byte at address 100:

  Main memory:
    addresses:   ... 60 61 62 63 | 64 65 66 ... 100 ... 127 | 128 ...
                                  +---------------------------+
                                  |       cache line          |
                                  |     (64 bytes total)      |
                                  +---------------------------+
                                                  |
                                  Hardware copies the WHOLE
                                  64-byte aligned block into:
                                                  v
  L1 cache:                       +--------------------------------------------+---------------+
                                  | tag = high address bits (block number 1)   | bytes 64..127 |
                                  +--------------------------------------------+---------------+

  Now any access to address 64..127 is a cache hit:
  - read byte 100  ->  HIT
  - read byte 101  ->  HIT (spatial locality!)
  - read byte 115  ->  HIT

  Reading byte 200 would be a MISS; the hardware would fetch
  another aligned 64-byte line containing address 200.

In reality, caches are much larger than this and so it would be inefficient to just fill up the entire cache with one block of memory. Caches are broken into cache lines which are the smallest block of memory that can be read from or written to memory. On modern x86 CPUs, cache lines are 64 bytes. Historically, cache line sizes have ranged from 32 to 128 bytes on various architectures. The process's memory is broken up into line-size portions of blocks and mapped to one or more cache lines. In the next section, we will talk about how memory is mapped to cache line(s).

Cache Mapping

There are three types of mapping schemes:

  • Direct-Mapped: Here more than one memory block is mapped to one and only one cache line. Usually this is done by using the middle bits of the first address of a memory block and finding the corresponding cache line index. Since more than one part of memory can be located in this line, there is also a corresponding tag value, typically the upper bits of the address, that is written into the cache line for the CPU to determine which block of memory is in the cache.
    When the CPU looks for a value, it determines the index from the middle bits of the address, then it finds the cache line. It then compares the tag in the cache line to the tag from the address. If they match then this is a hit and the value is used. If the tags don't match, then it will evict the current block by overwriting it with the new memory block, updating the tag to the new block. A tag mismatch is a miss, but not always the same kind of miss: it could be a compulsory miss (the block has never been loaded before) or a capacity miss (the working set is simply too big for the cache). It is a conflict miss when the block was evicted because another block mapped to the same index, even though the rest of the cache still had room. 
      Address breakdown for a direct-mapped cache:

   high bits         middle bits         low bits
   +---------+------+--------------+----+----------+
   |   tag   |        set index    |  block offset |
   +---------+------+--------------+----+----------+

   ^^^^^^^^^                       ^^^^^^^^^^^^^^^^
   compared to tag stored          which byte within
   in the cache line               the 64-byte line

  Direct-mapped cache (4 lines, for illustration only):

       index  | valid |  tag  | data (64 bytes)
       -------+-------+-------+------------------
         00   |   1   | 0x4A  | ...
         01   |   1   | 0x12  | ...
         10   |   0   |  -    |  (empty)
         11   |   1   | 0x4A  | ...

  Two memory blocks with different tags but the SAME middle
  bits both map to the same row. Each new arrival kicks out
  the previous occupant. That's a conflict miss.
  • Set Associative Mapping: Direct mapping causes a lot of conflict misses. To help avoid this problem, caches use set associative mapping. Here the cache is grouped into sets of cache lines. Each line can hold one chunk of memory that can be read and written to. Each set has a fixed number of lines. Set associative caches are called N-way associative caches where N is the number of lines in each set.
    • For example, instead of having one index map to one cache line, you can have one index map to 2 cache lines (2-way associative). This way if there is already a block in one cache line, the new block can be stored in the other cache line. This helps to reduce conflict misses. However, if all cache lines fill up, then the hardware has to determine which of the cache line's block of data to evict (overwrite with the new data). Hardware caches typically use least recently used (LRU) or, more commonly in practice, a cheaper approximation like pseudo-LRU, FIFO, or random replacement. (LFU — least frequently used — is more often seen in software caches such as page replacement and web caches; it is rare in hardware.) 
        2-way set-associative cache (2 sets, 2 ways per set):

   set 0:  +-------+-------+    +-------+-------+
           | tag A | data  |    | tag B | data  |
           +-------+-------+    +-------+-------+
                way 0                way 1

   set 1:  +-------+-------+    +-------+-------+
           | tag C | data  |    | tag D | data  |
           +-------+-------+    +-------+-------+

  An address hashes to a SET (using the middle bits) and can
  live in EITHER way within that set. On miss, the LRU
  occupant of the set is evicted.

  An N-way set-associative cache with one set is the same as
  fully-associative; an N-way set-associative cache with one
  way is the same as direct-mapped.
  • Fully Associative Mapping: This mapping scheme does away with mapping altogether. Each memory block can be put into any cache line. This is not used much because of the huge cost of searching the entire cache to find the correct block losing the main purpose of having a cache: quick access. Typically, caches are N-way set associative. 
      Fully associative cache (one set with all the ways):

      +-------+-------+ +-------+-------+ +-------+-------+ ...
      | tag P | data  | | tag Q | data  | | tag R | data  |
      +-------+-------+ +-------+-------+ +-------+-------+ ...

  Any incoming block can occupy any line. To check for a hit
  the hardware compares the address tag against EVERY tag in
  parallel. Great hit rates, but expensive in transistors --
  this is why fully associative is used only for small
  structures (e.g., the TLB) or not at all.

Worked Example: Decoding an Address

Let's put the tag, set index, and block offset pieces together with real numbers. Suppose we have a 32 KB, 4-way set-associative cache with 64-byte cache lines, and 32-bit addresses. First, work out the geometry of the cache:

  Total lines:  32768 bytes / 64 bytes per line = 512 lines
  Sets:         512 lines / 4 lines per set     = 128 sets

  Block offset bits:  64 bytes per line = 2^6   ->  6 bits
  Set index bits:     128 sets = 2^7             ->  7 bits
  Tag bits:           32 - 7 - 6                 -> 19 bits

Now decode the address 0x1234ABCD with this breakdown:

  0x1234ABCD = 0001 0010 0011 0100 1010 1011 1100 1101

  |     19 tag bits     | 7 index bits | 6 offset bits |
  | 0001001000110100101 |   0101111    |    001101     |

The low 6 bits (001101 = 13) select the byte within the 64-byte line. The next 7 bits (0101111 = 47) select the set. The remaining 19 high bits form the tag, 0x91A5. So to look up this address, the hardware goes to set 47, compares 0x91A5 against the tags of the 4 lines in that set, and if one matches (and is valid), it's a hit — the requested value is at byte 13 of that line.

Three Kinds of Cache Misses

Cache misses are traditionally categorized into three Cs:

  • Compulsory miss (cold miss): the very first reference to a block. The block has never been in the cache before, so it must be fetched. Even an infinitely large cache cannot avoid these.
  • Capacity miss: the program's working set is larger than the cache, so blocks that were evicted are later re-referenced. Increasing cache size reduces these.
  • Conflict miss: the cache has room overall, but the specific set the block maps to is full because too many active blocks share the same index. Increasing associativity reduces these (a fully-associative cache has none).

Cache Writes

The above mapping works for both reading and writing to memory. For reading, this isn't too much of a problem but for writing, we need to decide if and when we should update main memory. Since we are trying to avoid accessing main memory, we don't want to do a write every time a value is updated (this is called write through). For example, what if the value is written to over and over again? We would be wasting time writing a value that would be written over again soon. On the other hand, we may need to read the updated value later in the running of the program so we do need to update memory at some point.

One way to avoid excessive writes to memory is to wait until a line is evicted to update main memory. This is called a write back. This requires being able to keep track of whether a value has been updated by using a dirty bit. If this is set to 1, the value will be written back to main memory.

There's also the question of what happens on a write miss (when the address being written to is not in the cache). With write-allocate (also called "fetch on write"), the cache first loads the block from the next level into the cache, then performs the write on the cached copy. This is typically paired with write-back. With no-write-allocate (also called "write around"), the write goes directly to the next level of memory without loading the block into the cache. This is typically paired with write-through.
